## Development Setup

### Prerequisites

- .NET 8 SDK or later
- Visual Studio 2022 (Enterprise/Professional/Community) or Visual Studio Code
- Git command line
- Azure DevOps CLI (optional, for artifact inspection)

### Local Development

1. Clone the repository:
   ```bash
   git clone https://github.com/lmkr2026-byte/SharedLogging.git
   cd SharedLogging
   ```

2. Restore dependencies:
   ```bash
   dotnet restore
   ```

3. Build:
   ```bash
   dotnet build --configuration Release
   ```

4. Local package generation (for testing):
   ```powershell
   ./build/pack.ps1 -Configuration Release -OutputPath ./bin/packages
   ```

## Making Changes

### File Structure

```
src/LMKR.Shared.Logging/
├── Attributes/           # [Obsolete] markers, feature flags
├── Configuration/        # SharedLoggingOptions, config models
├── Extensions/           # IServiceCollection, IApplicationBuilder extensions
├── Interceptor/          # gRPC logging interceptors
├── Middleware/           # HTTP middleware (CorrelationId, RequestResponse, etc.)
├── Models/               # Data models (ApiLogModel, ResponseModel)
├── Repositories/         # Data access layer for logging storage
└── Exceptions/           # Custom exception types
```

### Code Style

- Follow existing code patterns (look at existing middleware/extensions)
- Use XML documentation comments on public APIs:
  ```csharp
  /// <summary>
  /// One-line description of what this does.
  /// </summary>
  /// <param name="param">Description of parameter.</param>
  /// <returns>Description of return value.</returns>
  public void DoSomething(string param)
  {
	  // Implementation
  }
  ```
- Enable nullable reference types (`#nullable enable` at top of new files)
- Use implicit usings (enabled in `.csproj`)

### Logging Best Practices

When adding new logging:

```csharp
// Use Serilog's structured logging
Log.Information("Request started: {@HttpRequest}", request);

// Avoid string interpolation for structured data
// Good:
Log.Error(ex, "Operation failed for user {UserId}", userId);

// Bad:
Log.Error($"Operation failed for user {userId}");
```

## Semantic Versioning & Commit Messages

**IMPORTANT:** Do NOT manually bump versions in `.csproj`. Instead, use semantic commit messages. GitVersion will automatically calculate and apply the correct version during the CI/CD pipeline.

### Semantic Versioning

This project uses [Semantic Versioning](https://semver.org/):
- **MAJOR** version: Incompatible API changes (breaking changes)
- **MINOR** version: Backward-compatible functionality additions
- **PATCH** version: Backward-compatible bug fixes

### Commit Message Format

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
type(scope): subject

body

footer
```

#### Types

- `feat`: A new feature (results in MINOR version bump)
- `fix`: A bug fix (results in PATCH version bump)
- `docs`: Documentation changes (no version bump if only docs)
- `style`: Code style changes that don't affect functionality
- `refactor`: Code refactoring without feature changes
- `perf`: Performance improvements
- `test`: Adding or updating tests
- `chore`: Build process, dependencies, tooling

#### Examples

**Patch (1.0.0 → 1.0.1):**

```
fix: prevent null reference in CorrelationIdMiddleware when header is missing

- Check for null/empty correlation ID before assignment
- Add unit test for null header scenario
- Log warning when correlation ID is autogenerated
```

**Minor (1.0.0 → 1.1.0):**

```
feat: add configurable request timeout to logging middleware

This allows services to specify custom timeout values per middleware registration.

New config option: SharedLoggingOptions.RequestTimeoutMs (default: 30000)
```

**Major (1.0.0 → 2.0.0) - See "Breaking Changes" below:**

```
feat: restructure RequestLoggingOptions configuration

BREAKING CHANGE: The RequestLoggingOptions class has been renamed to 
LoggingRequestOptions and several properties have been renamed:
- IsEnabled → EnableLogging
- MaxBodySize → MaxRequestBodyBytes
- IncludeHeaders → LogHeaders

Consumers must update their appsettings.json and any code referencing these properties.
See CHANGELOG.md for detailed migration guide.
```

### Version Bump Explicit Control

If Conventional Commits don't clearly indicate the version bump, use explicit prefixes:

```bash
# Force a patch bump:
git commit -m "+semver:patch fix: minor improvement"

# Force a minor bump:
git commit -m "+semver:minor chore: update dependency"

# Force a major bump:
git commit -m "+semver:major Big refactor with required code changes"
```

## Breaking Changes

Breaking changes are **major version** changes and must be carefully planned.

### Identifying Breaking Changes

A change is breaking if:

- Removing a public class, method, or property
- Changing the signature of a public method
- Changing the return type of a public method
- Removing or renaming a configuration section
- Changing default behavior in a way that breaks existing code
- Changing dependency versions that themselves introduce breaking changes

### Declaring Breaking Changes

**In commit message:**

```
feat: redesign CorrelationIdMiddleware API

BREAKING CHANGE: The CorrelationIdMiddleware constructor signature has changed.
- Old: CorrelationIdMiddleware(RequestDelegate next)
- New: CorrelationIdMiddleware(RequestDelegate next, ICorrelationIdGenerator generator)

Consumers must update their middleware registration code.
```

**In CHANGELOG.md:**

Add to the version section with a "Breaking Changes" or "Migration Guide" subsection:

```markdown
## [2.0.0] - 2024-02-XX

### BREAKING CHANGES

- **Removed:** `SharedLoggingOptions.LegacyFormat` property (use `Format` instead)
- **Renamed:** `RequestLoggingMiddleware` → `HttpRequestLoggingMiddleware`
- **Changed:** `IApiLoggingRepository.LogAsync()` now returns `Task<Guid>` instead of `Task<bool>`

### Migration Guide

#### For existing consumers:

1. Update `appsettings.json`:
   ```json
   // Old
   "SharedLogging": { "LegacyFormat": "json" }

   // New
   "SharedLogging": { "Format": "json" }
   ```

2. Update middleware registration in `Program.cs`:
   ```csharp
   // Old
   app.UseMiddleware<RequestLoggingMiddleware>();

   // New
   app.UseMiddleware<HttpRequestLoggingMiddleware>();
   ```
```

### Deprecation Strategy

For major refactors, consider deprecating before removing:

**Version 1.5.0:** Add deprecation warning
```csharp
[Obsolete("Use NewClassName instead. Will be removed in v2.0.0", false)]
public class OldClassName
{
	// Implementation with warning but still functional
}
```

**Version 2.0.0:** Remove the deprecated class

This gives consuming services 1-2 release cycles to update their code.

## Pull Request Process

1. **Create a feature branch** from `main`:
   ```bash
   git checkout -b feature/add-request-timeout-config
   ```

2. **Make your changes** with meaningful commits (follow semantic commit guidelines)

3. **Ensure code quality:**
   ```bash
   dotnet build --configuration Release
   dotnet test (if tests exist)
   ./build/pack.ps1  # Test local packaging
   ```

4. **Push and create a PR:**
   ```bash
   git push origin feature/add-request-timeout-config
   # Then create PR via GitHub UI
   ```

5. **PR Description Template:**
   ```markdown
   ## Summary
   Brief description of what this PR does.

   ## Type of Change
   - [ ] Bug fix (non-breaking)
   - [ ] New feature (non-breaking)
   - [ ] Breaking change
   - [ ] Documentation update

   ## Testing
   - [ ] Local build passes
   - [ ] Tests pass (if applicable)
   - [ ] Tested against sample microservice

   ## Breaking Changes (if applicable)
   - [ ] Documented in CHANGELOG.md
   - [ ] Migration guide provided
   - [ ] Consuming services notified

   ## Checklist
   - [ ] Code follows style guidelines
   - [ ] Self-review completed
   - [ ] Comments added for complex logic
   - [ ] CHANGELOG.md updated (for feature/fix)
   - [ ] No breaking changes without proper documentation
   ```

6. **Code Review:**
   - Address review comments
   - Push new commits (don't force-push unless requested)
   - Re-request review after changes

## Release Process

**Note:** Releases are automated via Azure Pipelines. This is for reference/understanding.

1. **Merge to main** - Your PR with properly formatted commits is merged to `main`

2. **Azure Pipelines triggers:**
   - GitVersion calculates version from commit history
   - Build and test runs
   - `.nupkg` created with semantic version
   - Package pushed to `LMKR-Shared-Packages` feed

3. **GitHub Dependabot notifies consumers:**
   - Scan consuming service repos
   - Create PRs to update version
   - Teams review and merge

4. **Consuming services deploy:**
   - Each service's CI/CD rebuilds
   - New version of LMKR.Shared.Logging is included

### Hotfixes

For urgent patches (e.g., security fixes):

1. Create a branch from the previous stable tag:
   ```bash
   git checkout v1.0.2
   git checkout -b hotfix/security-fix
   ```

2. Make and commit the fix (follow commit message guidelines):
   ```bash
   git commit -m "fix: patch XXE vulnerability in Serilog config parsing"
   ```

3. Create PR against `main`

4. After merge, Azure Pipelines will:
   - Detect the hotfix commit
   - Calculate new patch version (1.0.2 → 1.0.3)
   - Publish immediately
